# Глава 0. Предисловие

Добро пожаловать на курс по написанию бекенда на Rust. За время курса мы пройдём путь от первого `Hello, World!` на Axum до полноценного REST API пиццерии с базой данных, аутентификацией и тестами.
## Для кого этот курс

Этот курс для тех, кто уже знаком с основами Rust и теперь хочет перейти от небольших программ и CLI-утилит к написанию REST API.

Курс подойдёт:
- Backend-разработчикам из других языков (Go, Python, Node.js, Java, C#), которые хотят попробовать Rust
- Rust-разработчикам без бекенд-опыта - писали CLI, эмбеддед, что-то системное, а теперь заинтересовались веб-разработкой
- Студентам и самоучкам, которые уже освоили основы Rust и хотят посмотреть на другой подход к разработке бекенда

Если Rust ваш первый язык программирования, то советую отложить этот курс на потом. Это не снобизм и не попытка вас отговорить от изучения Rust. Rust - язык сложный и с большой кривой изучения. Он заставляет держать в голове много сложных вещей: владение и заимствование, времена жизни, трейты и обобщения, алгебраические типы и т.д. Всё это решения проблем, с которыми вы ещё не сталкивались. Borrow checker защищает вас от многих ошибок, но чтобы понять, за что благодарить компилятор, нужно хотя бы раз наступить на висячий указатель или на мутацию списка во время итерации по нему. Без этого опыта правила языка выглядят как набор произвольных придирок, а обучение превращается в «угадай, куда поставить `&`, чтобы собралось». Начните с Python или Go, напишите на нём что-нибудь работающее, а потом возвращайтесь.

## Зачем вообще писать бекенд на Rust

- Многие ошибки становятся частью системы типов. То, что в других языках приходится искать тестами или ловить в проде, в Rust обнаруживается ещё на этапе компиляции: [`Option` вместо `null` и `Result` вместо исключений](https://habr.com/ru/articles/1045718/), отсутствие неявных приведений типов. Например, функция поиска пользователя может ничего не найти:
```rust
fn find_user(id: u64) -> Option<User> { ... }

let user = find_user(1);
println!("{}", user.name); // не скомпилируется: сначала нужно обработать случай None
```
В Python аналогичный `find_user(1).name` запустится без проблем и упадёт с `AttributeError` только тогда, когда пользователь действительно не найдётся, то есть скорее всего в проде. Rust не делает программу правильной автоматически, логические ошибки никуда не исчезают. Но значительный класс ошибок просто невозможно выразить в коде, который скомпилировался
- Рефакторинг перестаёт быть страшным. Это вытекает из прошлого пункта, вы меняете тип поля в структуре, запускаете `cargo check`, получаете список из сорока мест, чините их и скорее всего всё работает. Это свойство чувствуется не на первой неделе, а на шестом месяце жизни проекта, когда кодовая база выросла, а вы уже забыли, как работает половина
- Отсутствие гонок данных. Система типов предоставляет трейты-маркеры [`Send` и `Sync`](https://doc.rust-lang.org/nomicon/send-and-sync.html), которые описывают, какие данные можно передавать и разделять между потоками. Все проверки происходят на этапе компиляции и не стоят ничего во время выполнения. Важно понимать, что речь именно о data race, то есть об одновременной записи в одну память. Логические гонки, например две параллельные транзакции в базе данных, по-прежнему остаются на вас
- Предсказуемое потребление ресурсов. В Rust нет сборщика мусора, поэтому нет внезапных пауз на сборку мусора и нет загадочного роста памяти под нагрузкой. Rust-сервис обычно держит задержки ровно там, где вы их замерили, а не улетает в стратосферу на 95-м перцентиле. Например, Discord [переписал](https://habr.com/ru/articles/487116/) некоторые свои высоконагруженные сервисы с Go на Rust: сборщик мусора Go запускался примерно раз в две минуты и вызывал регулярные скачки задержки
- Один бинарник на выходе. Итог сборки один исполняемый файл. Не нужен рантайм в контейнере, не нужен `node_modules`, не нужно виртуальное окружение
## Где уже используется Rust

* Discord [переписал](https://habr.com/ru/articles/487116/) некоторые свои высоконагруженные сервисы с Go на Rust: сборщик мусора Go запускался примерно раз в две минуты и вызывал регулярные скачки задержки
* Cloudflare написала на Rust http-прокси [Pingora](https://blog.cloudflare.com/how-we-built-pingora-the-proxy-that-connects-cloudflare-to-the-internet/), который заменил nginx и обрабатывает более триллиона запросов в день. По данным самой компании, при той же нагрузке он потребляет примерно на 70% меньше CPU и на 67% меньше памяти
* Figma [вынесла](https://www.figma.com/blog/rust-in-production-at-figma/) производительно-критичную часть сервера совместного редактирования (сериализацию документов) в отдельный процесс на Rust. Сервер целиком работал на TypeScript и на больших файлах возникали непредсказуемые скачки задержки. После переноса сериализация стала в 10 раз быстрее
* Dropbox [переписал](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine) с Python на Rust движок синхронизации файлов Nucleus. Среди причин, возможность выразить сложные инварианты синхронизации в системе типов, чтобы их проверял компилятор
* AWS создала на Rust [Firecracker](https://github.com/firecracker-microvm/firecracker) - технологию виртуализации, на которой работают AWS Lambda и AWS Fargate
* npm [переписал](https://www.rust-lang.org/static/pdfs/Rust-npm-Whitepaper.pdf) на Rust сервис авторизации публикации пакетов, который был узким местом по CPU. Команда сравнивала Node.js, Go и Rust, и среди причин выбора Rust называет удобную работу с зависимостями
* Svix - сервис для отправки и приёма webhooks, написан на Rust и Axum. Проект есть в списке [awesome-axum](https://github.com/szabgab/awesome-axum)
## А теперь про производительность

Rust быстрый, возможно вы не раз видели это в бенчмарках, где он стабильно сидит в верхушке любого рейтинга. Но скорее всего вам эта скорость не понадобится.

Существует целый жанр pet-проектов - высокопроизводительный сервис, способный держать 200.000 RPS, задеплоенный на VPS за 5 долларов, с суточной аудиторией в одного автора и его маму. В подавляющем большинстве настоящих бекендов узкое место - это не язык, а база данных, сеть, внешнее api и т.д. Переписав сервис с Python на Rust вы получите более стабильный latency, выоскую производительнсть и меньшее потребление памяти, но это не имеет смысла, если у проекта нагрузка 20 запросов в день.

Поэтому главный аргумент за Rust на бекенде не скорость, а надёжность: компилятор не даёт выстрелить себе в ногу, а работающий сервис дёшево поддерживать. Производительность - приятный бонус.
## Когда бекенд на Rust плохая идея

- Скорость разработки. Если Rust для вас не основной язык, писать на нём существенно медленнее, чем на других языках. Разбор того, почему `&str` не живёт достаточно долго и как правильно вернуть ошибку из хендлера, может съесть много времени и нервных клеток. Разрыв сокращается с опытом и почти исчезает на больших проектах. Например, мне нет разницы, на чём писать бекенд: на FastAPI или на Axum. Но для новичков в языке это может быть большой сложностью
- Время компиляции. Проект средних размеров (пара десятков тысяч строк кода) собирается достаточно долго, тем более на слабом компьютере. Инкрементальная сборка и `cargo check` быстрее, но скрипт на Python или проект на Go будут запускаться значительно быстрее. Rust - один из самых долго компилируемых языков программирования
- Найм. Rust-разработчиков на рынке немного, а вакансий на рынке РФ ещё меньше. Поэтому если вы изучаете Rust в первую очередь для поиска работы, то это не лучшая идея
- Незрелость части экосистемы. Библиотек меньше, чем в Python или JS. SDK для вашего вендора может не существовать и придётся ходить в его REST API руками. Удобных библиотек-обёрток уровня FastStream из Python нет или они слишком незрелы, поэтому придётся писать свои костыли

Общее правило: Rust хорош там, где код будет жить долго, стоимость ошибки в проде высокая, а нагрузка постоянная. Rust плох там, где требования меняются каждый день, а проект может быть выброшен через месяц.

## Что будет в курсе

1. Введение в Axum. Что это за фреймворк и чем он отличается от альтернатив, первый работающий сервер. Работа с JSON, роутинг, хендлеры и ответы, экстракторы, состояние приложения, обработка ошибок, настройка проекта
2. Работа с базой данных. PostgreSQL и `sqlx`: пул соединений, миграции, проверка запросов на этапе компиляции, транзакции, репозитории, маппинг ошибок БД в HTTP-ответы и пагинация
3. Аутентификация и авторизация. Хеширование паролей, сессии и JWT, refresh-токены, защита роутов
4. Продвинутые темы. Middleware, логирование, отладка, тестирование, загрузка файлов (multipart), WebSocket, SSE, фоновые задачи, graceful shutdown, шаблоны и т.д.
5. Мини-проект пиццерии. Собираем полноценное приложение на основе полученных знаний
